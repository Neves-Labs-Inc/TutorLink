## Task P2-T1.1 — Auth dependencies, settings, security primitives, and auth schemas

**Satisfies:** REQ-022, REQ-025
**Agent:** `coder-sr`
**Dependencies:** none — dispatchable immediately.

### Objective

Provide every pure, database-free auth primitive the rest of the phase imports: bcrypt
password hashing, JWT mint and verify, the three new `Settings` fields, and the two Pydantic
shapes that cross the HTTP boundary.

### Files owned (exclusive writable set)

```
api/pyproject.toml
api/uv.lock
api/app/config.py
api/app/security.py
api/app/schemas/auth.py
api/tests/test_security.py
```

Touch nothing else. In particular do **not** edit `api/app/main.py`, `api/app/db.py`,
`api/tests/conftest.py`, or anything under `api/app/models/` — other tasks own those and are
running at the same time.

### What to build

**1. Three new runtime dependencies in `api/pyproject.toml`, then `uv lock`.**

| Package | Why this one |
|---|---|
| `pyjwt>=2.9` | JWT encode/decode. Chosen over `python-jose`: actively maintained, fewer transitive dependencies, and it is what FastAPI's own security tutorial now uses |
| `bcrypt>=4.2` | Password hashing, called **directly** |
| `python-multipart>=0.0.9` | Required by FastAPI to parse `OAuth2PasswordRequestForm`; without it `/auth/token` raises at import time |

**Do not add `passlib`.** `passlib` is unmaintained and its bcrypt backend crashes against
`bcrypt>=4.1` with `AttributeError: module 'bcrypt' has no attribute '__about__'`. Use
`bcrypt.hashpw` / `bcrypt.checkpw` / `bcrypt.gensalt()` directly — it is a four-line wrapper
and it has no such trap. These three additions are recorded in `STATE.md` **D-020** as the
constitution requires; add nothing else.

This task is the **only** one in Phase 2 permitted to modify `api/pyproject.toml` or
`api/uv.lock`. If any other task finds a dependency missing, it stops and reports.

**2. `api/app/config.py` — three fields appended to `Settings`.**

`jwt_algorithm: str = "HS256"`, `access_token_expire_minutes: int = 15`,
`refresh_token_expire_days: int = 7`. All have defaults, so **no new environment variable is
introduced** and `.env.example`, `docker-compose.yml`, and `Readme.md` stay untouched
(D-016). Do not remove or reorder the existing fields; `get_settings()` stays `lru_cache`d.

**3. `api/app/security.py` — new module, exactly the surface frozen in `02-CONTEXT.md`.**

- `hash_password(plain) -> str` — `bcrypt.hashpw(plain.encode(), bcrypt.gensalt())`, decoded
  to `str` for the `String(255)` column.
- `verify_password(plain, hashed) -> bool` — `bcrypt.checkpw`; return `False` (never raise)
  when `hashed` is malformed or not a bcrypt hash, so a corrupt row is a failed login rather
  than a 500.
- `password_is_encodable(plain) -> bool` — `len(plain.encode("utf-8")) <= MAX_PASSWORD_BYTES`
  (72). bcrypt **silently truncates** past 72 bytes, which would make two different long
  passwords interchangeable. Callers reject rather than truncate.
- `DUMMY_PASSWORD_HASH` — a module-level bcrypt hash of an arbitrary constant string,
  computed once at import. `P2-T2.1` verifies against it when a user is not found so that
  login timing does not reveal whether an account exists.
- `create_access_token`, `create_refresh_token`, `decode_token` per the frozen signatures.
  Sign with `get_settings().secret_key` and `get_settings().jwt_algorithm`. Every timestamp
  is UTC (`datetime.now(datetime.UTC)`); `exp` and `iat` are integer epoch seconds.
- `decode_token` raises `TokenError` — never lets a `jwt.PyJWTError` escape — for a bad
  signature, an expired token, malformed JSON, a missing required claim, an unparseable UUID,
  **and for a `typ` that is not `expected_type`**. That last check is the one that stops a
  seven-day refresh token being replayed as an access token; it is not optional.

**4. `api/app/schemas/auth.py`** — `TokenPair` and `RefreshRequest`, exactly as frozen. Both
are Pydantic v2 models. Nothing else belongs in this file.

**5. `api/tests/test_security.py`** — pure unit tests, **no database, no fixtures from
`conftest.py`** (that file belongs to `P2-T1.3`, which is running concurrently). Cover at
minimum:

- A hash verifies against its own plaintext and fails against a different one.
- Two hashes of the same plaintext differ (salt is random) and both verify.
- `verify_password("x", "not-a-hash")` returns `False` rather than raising.
- `password_is_encodable` is `True` at 72 bytes and `False` at 73, using a multi-byte
  character to prove it counts **bytes**, not characters.
- An access token round-trips `sub`, `role`, and `tutor_id`, including `tutor_id=None`.
- `decode_token(access, expected_type="refresh")` raises `TokenError`, and vice versa.
- A token signed with a different secret raises `TokenError`.
- A token whose `exp` is in the past raises `TokenError` (freeze or backdate rather than
  sleeping).

### Acceptance criteria

- `docker compose run --rm api uv run pytest -q tests/test_security.py` passes.
- `docker compose run --rm api uv run ruff check .` clean.
- `docker compose run --rm api uv run python -c "import app.security, app.schemas.auth"` exits 0.
- `git diff --name-only` lists exactly the six owned files.
- `grep -rn "passlib" api/` returns nothing.
- `grep -rn "SECRET_KEY\|secret_key" api/app/security.py` shows the key reached only through
  `get_settings()`, never a literal.

### Out of scope

No database access of any kind in `security.py` — it imports nothing from `app.db` or
`app.models` except `UserRole` from `app.models.enums`. No FastAPI dependency, no router, no
`OAuth2PasswordBearer` (that is `P2-T2.2`). No revocation logic and no `refresh_tokens` model
(`P2-T1.2`). No changes to `.env.example`, `docker-compose.yml`, or `Readme.md`. No logging
of any token, hash, or password anywhere.

## Task P2-T1.2 — Refresh-token revocation store and migration `0002`

**Satisfies:** REQ-02A
**Agent:** `coder-jr`
**Dependencies:** none — dispatchable immediately. It needs only `Base` from `api/app/db.py`
and the `users` table, both of which shipped in Phase 1 at `684a015`.

### Objective

Give the system a server-side record of which refresh tokens are live, so that logout and
forced session termination take effect immediately instead of waiting out a seven-day token.

### Files owned (exclusive writable set)

```
api/app/models/refresh_token.py
api/app/models/__init__.py
api/alembic/versions/0002_refresh_tokens.py
api/tests/test_refresh_token_model.py
```

Do not edit `api/app/db.py`, `api/app/models/user.py`, `api/alembic/env.py`, or migration
`0001`. **Do not edit `api/pyproject.toml`** — this task needs no new dependency; if you
believe it does, stop and report.

### What to build

**`api/app/models/refresh_token.py`** — a `RefreshToken` model matching the frozen table
shape in `02-CONTEXT.md`, following the conventions already established in
`api/app/models/user.py`: `UUID(as_uuid=True)` primary key with
`server_default=text("gen_random_uuid()")`, `DateTime(timezone=True)` throughout,
`Mapped[...]` / `mapped_column(...)` 2.0 style, `from __future__ import annotations` plus a
`TYPE_CHECKING` import for the `User` relationship.

Columns, precisely:

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | **this value is the JWT `jti`** |
| `user_id` | UUID | `ForeignKey("users.id")`, `nullable=False`, indexed |
| `family_id` | UUID | `nullable=False`, indexed — every rotation descendant shares it |
| `issued_at` | TIMESTAMPTZ | `nullable=False`, `server_default=func.now()` |
| `expires_at` | TIMESTAMPTZ | `nullable=False` |
| `revoked_at` | TIMESTAMPTZ | `nullable=True` — `NULL` means live |
| `replaced_by_id` | UUID | `ForeignKey("refresh_tokens.id")`, `nullable=True` — rotation audit trail |

Add `user: Mapped[User] = relationship(back_populates=…)` **only if** you can add the
matching side without editing `user.py`, which you cannot — so use a one-directional
`relationship("User")` with no `back_populates`, or omit the relationship entirely. Omitting
it is acceptable and preferred: nothing in Phase 2 navigates from a token to a user object.

`replaced_by_id` is a self-referential FK; declare it with `remote_side` or leave it as a
plain column with no relationship. A plain column is enough.

There is **no `updated_at`** on this table. A refresh-token row is written once and revoked
once; there is nothing to update. Do not add one out of symmetry with the other nine tables.

**`api/app/models/__init__.py`** — add the `RefreshToken` import and its `__all__` entry,
keeping the existing alphabetical ordering and touching no other line. This file is how
`Base.metadata` learns the table exists; Alembic autogenerate and the test harness both
depend on it.

**`api/alembic/versions/0002_refresh_tokens.py`** — `revision = "0002"`,
`down_revision = "0001"`. `upgrade()` creates the table with both indexes and all three
foreign keys; `downgrade()` drops it. No enum is involved, so none of `0001`'s explicit
`CREATE TYPE` / `DROP TYPE` handling applies here. Do not create any extension —
`gen_random_uuid()` is core in PostgreSQL 13+ and the stack pins `postgres:17-alpine`.

**`api/tests/test_refresh_token_model.py`** — metadata-level only, mirroring the existing
`api/tests/test_models.py` style so it needs no live database and no `conftest.py` fixture
(`P2-T1.3` owns that file and is running concurrently). Assert that `refresh_tokens` is in
`Base.metadata.tables`, that the seven columns exist with the expected nullability, that
`revoked_at` is nullable while `expires_at` is not, and that `user_id` and `family_id` are
each indexed.

### Acceptance criteria

- `docker compose run --rm api alembic upgrade head` on an already-migrated database applies
  `0002` and reports `Running upgrade 0001 -> 0002`.
- `docker compose run --rm api alembic check` reports no pending autogenerate diff — model
  and migration agree.
- `docker compose run --rm api alembic downgrade 0001` drops `refresh_tokens` and leaves the
  nine Phase 1 tables intact; re-upgrading works.
- From an **empty** database, `alembic upgrade head` produces ten tables plus
  `alembic_version`, and `alembic downgrade base` leaves only `alembic_version`.
- `docker compose run --rm api uv run pytest -q tests/test_refresh_token_model.py` passes.
- `docker compose run --rm api uv run ruff check .` clean.
- `git diff --name-only` lists exactly the four owned files.

### Out of scope

No service logic, no rotation, no revocation queries — `P2-T2.1` owns all of that. No router.
No change to `users` or any Phase 1 model. No storing of a token string or a token hash in
this table, ever: the row holds a `jti` and nothing more. No cleanup job or TTL sweeper for
expired rows (a Phase 8 concern at the earliest; note it and move on).

## Task P2-T1.3 — Live-PostgreSQL pytest harness

**Satisfies:** REQ-024, REQ-02A — as enabling infrastructure. This task ships **no product
behaviour**; it exists because rotation, reuse detection, revocation, and the RBAC dependency
are all database behaviour, and metadata-level assertions cannot prove any of them. It is
listed here rather than buried inside another task because three downstream tasks depend on
it and it must not be re-invented three times.

**Agent:** `coder-sr`
**Dependencies:** none — dispatchable immediately.

### Objective

Add database-backed fixtures to the existing pytest setup without disturbing the eight Phase 1
tests, so that Phase 2 (and every later phase) can assert against real rows.

### Files owned (exclusive writable set)

```
api/tests/conftest.py
```

One file. Do not touch any existing test module, any application module, or
`api/pyproject.toml` — `pytest` is already a dev dependency and nothing new is needed.

### What to build

Extend `api/tests/conftest.py`, which currently sets three environment variables and exposes
a single `client` fixture, with:

**`_test_engine` (session-scoped).** Derives a test database name from
`get_settings().database_url` by appending `_test` to the database component. Connects to the
configured database with `isolation_level="AUTOCOMMIT"`, issues
`CREATE DATABASE <name>` when it does not already exist (tolerating the race), then builds and
yields an `Engine` bound to it. Imports `app.models` so every table — including
`refresh_tokens` once `P2-T1.2` lands — is registered, then calls
`Base.metadata.create_all(engine)`.

`create_all` in tests is explicitly permitted by the constitution and is the right tool here;
the migration is verified separately by `P2-T1.2`'s Verification section. Do **not** shell out
to Alembic from a fixture.

**`db` (function-scoped).** Opens a connection, begins a transaction, binds a `Session` to
that connection, yields it, then rolls the transaction back and closes. Every test therefore
starts from the same clean state and no test can leak rows into another. Do not
`create_all` / `drop_all` per test — it is slow and it defeats the rollback.

**`api` (function-scoped).** A `TestClient(app)` with `app.dependency_overrides[get_db]`
pointing at the same `db` session, cleared in teardown so overrides never leak between tests.
Import `app.main` lazily inside the fixture, matching the existing `client` fixture's comment
about `app.db` building its engine at import time.

**Leave the existing `client` fixture exactly as it is.** `api/tests/test_health.py` depends
on it and must keep passing untouched. The three `os.environ.setdefault` lines at the top stay
as well — they are what lets the pure-unit test modules import `app.config` with no
environment at all.

Session-scoped fixtures only execute when a test requests them, so
`pytest tests/test_security.py` must still pass with **no** database running. Confirm that.

### Acceptance criteria

- `docker compose run --rm api uv run pytest -q` — all Phase 1 tests still pass, unchanged.
- With the stack up, a scratch test that inserts a `User` through the `db` fixture and reads
  it back passes; running it twice in a row also passes, proving the rollback works. Delete
  the scratch test before finishing — this criterion is about proving the fixture, not about
  shipping the test.
- `docker compose run --rm api uv run pytest -q tests/test_health.py` passes with no test
  database created (the session fixture was never requested).
- `docker compose exec postgres psql -U $POSTGRES_USER -l` shows `tutorlink_test` after a run

- `docker compose run --rm api uv run ruff check .` clean.
- `git diff --name-only` lists exactly `api/tests/conftest.py`.

### Out of scope

No test for any Phase 2 feature — the tasks that own those features own their tests. No

## Verification

**Changed-risk surface.** Two things here are expensive to get wrong. First, the migration:
every later phase builds on the schema, and `0002` is the first migration after the initial
one, so it is also the first real test of the migration chain. Second, `security.py`: a
`decode_token` that does not enforce `typ` turns a seven-day refresh token into an
indefinitely-usable access token, and that failure is silent.

**Commands, narrowest first** — all in-container, from the repository root:

1. `docker compose run --rm api uv run ruff check .`
2. `docker compose run --rm api uv run pytest -q tests/test_security.py` — must pass with the
   database **stopped**, proving `security.py` has no database coupling.
3. `docker compose run --rm api uv run pytest -q`
4. `docker compose run --rm api alembic upgrade head` → `Running upgrade 0001 -> 0002`
5. `docker compose run --rm api alembic check` → no pending diff
6. `docker compose run --rm api alembic downgrade 0001`, then `alembic upgrade head` again
7. `docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c '\d refresh_tokens'`
   — confirm seven columns, both indexes, the FK to `users`, and the self-FK
8. `docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c '\dt'` — ten
   business tables plus `alembic_version`
9. `docker compose run --rm api uv run python -c "import app.security as s; import jwt; t=s.create_refresh_token(user_id=__import__('uuid').uuid4(), jti=__import__('uuid').uuid4(), family_id=__import__('uuid').uuid4())[0]; s.decode_token(t, expected_type='access')"`
   — must raise `TokenError`, not return claims

**Full-cycle smoke:** `docker compose down -v && docker compose up -d` then
`docker compose run --rm api alembic upgrade head` — ten tables from empty, no manual step.

**PASS requires:**

- **REQ-022** — an access token round-trips `sub`, `role`, and `tutor_id` (including a null
  `tutor_id`) and carries a future `exp`.
- **REQ-025** — passwords are bcrypt-hashed, verify correctly, and no plaintext or hash
  appears in any log line or test output.
- **REQ-02A** (schema half) — `refresh_tokens` exists after `upgrade head`, `alembic check` is
  clean, and `downgrade base` from empty leaves only `alembic_version`.
- Step 9 raising `TokenError` is a **hard gate**. A `decode_token` that accepts a refresh
  token where an access token was expected is a security defect, not a style issue, and fails
  the plan regardless of everything else.
