## Task T1.1 — FastAPI application skeleton, configuration, and connections

**Satisfies:** REQ-001, REQ-002, REQ-003, REQ-004, REQ-005
**Agent:** `coder-sr`
**Dependencies:** none — dispatchable immediately.

### Objective

Stand up a FastAPI service that boots from typed environment configuration, owns one
PostgreSQL engine and one Redis client, and proves both connections through a readiness
endpoint.

or anything at the repository root. Those belong to T1.2 and T3.1.

### What to build

**`api/pyproject.toml`** — project name `tutorlink-api`, `requires-python = ">=3.12,<3.13"`.
Declare **all** Phase 1 backend dependencies here so no later task has to touch this file:
`fastapi`, `uvicorn[standard]`, `sqlalchemy>=2.0`, `psycopg[binary]`, `alembic`,
`pydantic-settings`, `redis`. Dev group: `pytest`, `httpx`, `ruff`. Configure `ruff` in the
same file (line length 100, target `py312`). Generate `api/uv.lock` with `uv lock`.

**`api/app/config.py`** — a pydantic-settings `BaseSettings` subclass `Settings` with
fields, in this exact naming, read from the environment:

| Field | Type | Required |
|---|---|---|
| `database_url` | `str` | yes |
| `redis_url` | `str` | yes |
| `secret_key` | `str` | yes |
| `debug` | `bool` (default `False`) | no |
| `twilio_account_sid` | `str \| None` | no |
| `twilio_auth_token` | `str \| None` | no |
| `twilio_whatsapp_number` | `str \| None` | no |

Twilio fields are optional in Phase 1 because there is no webhook yet; they become required
in Phase 7. Expose `get_settings()` wrapped in `functools.lru_cache`. A missing required
variable must raise at import/startup with pydantic's message naming the field — do not add
fallback defaults for `database_url`, `redis_url`, or `secret_key`.

**`api/app/db.py`** — exactly these exports:
- `Base` — a single `class Base(DeclarativeBase)`. This is the only declarative base in the
  codebase; T1.2's models import it from here.
- `engine = create_engine(get_settings().database_url, pool_pre_ping=True)`
- `SessionLocal = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)`
- `get_db()` — a generator dependency that yields a session and closes it in a `finally`.
- `check_database() -> bool` — opens a session, runs `text("SELECT 1")`, returns success.

**`api/app/redis_client.py`** — `redis_client = redis.Redis.from_url(get_settings().redis_url,
decode_responses=True)` and `check_redis() -> bool` wrapping `PING`.

**`api/app/routers/health.py`** — an `APIRouter`:
- `GET /health` → `{"status": "ok"}`. Touches nothing. Never returns non-200 while the
  process is alive.
- `GET /health/ready` → calls `check_database()` and `check_redis()`. Both true → 200
  `{"database": "ok", "redis": "ok"}`. Either false → **503** with that dependency's value
  set to `"error"` (return a `JSONResponse` with an explicit status code; do not raise a
  bare `HTTPException` that loses the per-dependency detail).

**`api/app/main.py`** — build the `FastAPI` app with `title="TutorLink API"`, include the
health router, and expose `/docs`. Do **not** add CORS middleware: per D-012 the browser
reaches the API same-origin through the Vite proxy. Leave a one-line comment saying so, so
the next agent does not "helpfully" add a wildcard.

**Empty package markers** — `api/app/schemas/__init__.py` and `api/app/services/__init__.py`
exist to fix the layering from the constitution before any router is written. Empty files
with a one-line docstring are correct here; do not invent contents.

**Tests** — `api/tests/test_health.py` using `fastapi.testclient`: `/health` returns 200,
and `/health/ready` returns 503 with `redis: "error"` when `check_redis` is monkeypatched
to `False`. `conftest.py` sets the required env vars so `Settings` constructs under test.
Do not require a live database for these tests.

### Acceptance criteria

- `uv run uvicorn app.main:app` (from `api/`, with env set) starts without error.
- `GET /health` → 200 `{"status":"ok"}`.
- `GET /health/ready` → 200 with both dependencies `ok` when Postgres and Redis are up.
- Unsetting `DATABASE_URL` and starting the app produces a startup error naming
  `database_url`, not an `AttributeError` or a connection error later.
- `uv run pytest` passes. `uv run ruff check .` is clean.
- `from app.db import Base` works and is the only `DeclarativeBase` in the tree.

### Out of scope

No CORS middleware. No authentication, no JWT, no `OAuth2PasswordBearer`. No `/api/*`
routes. No models — not even a placeholder `User`. No Alembic. No logging framework beyond
uvicorn's default. No Dockerfile. No `.env` file of any kind.

## Task T1.2 — SQLAlchemy models for the full ERD and the initial migration

**Satisfies:** REQ-006, REQ-007, REQ-008
**Agent:** `coder-jr`

### What to build

Source of truth is `/Users/franklin.filho/Docs/Freelance/MsHelpingHands/TutorLink/docs/erd.md`.
Reproduce every column, type, nullability, foreign key, unique constraint, and index it
lists, with these explicit interpretations already decided (see `STATE.md` D-010, D-011):

- All primary keys are `UUID` with `server_default=text("gen_random_uuid()")`. The
  migration's first operation is `CREATE EXTENSION IF NOT EXISTS pgcrypto`.
- All `created_at` / `updated_at` are `TIMESTAMP WITH TIME ZONE`, `server_default=now()`,
  and `updated_at` additionally carries `onupdate`.
- `user_role` enum: `admin`, `tutor`. `booking_status` enum: `pending`, `confirmed`,
  `cancelled`, `completed`. Native PostgreSQL enums, created and dropped explicitly in the
  migration (`sa.Enum(..., name=..., create_type=False)` plus explicit `CREATE TYPE` /
  `DROP TYPE`, so downgrade is clean).
- `tutor_subjects.grade_levels` is `ARRAY(String)` (`sqlalchemy.dialects.postgresql.ARRAY`).
- `tutors`: implement `email` and `phone_number` as **two separate** unique constraints,
  not the composite the ERD text shows. `users.email` and `parents.phone_number` and
  `subjects.name` are unique. `tutor_subjects` is unique on `(tutor_id, subject_id)`.
  `tutor_availability` is unique on `(tutor_id, day_of_week, start_time)`.
- `users.tutor_id` → `tutors.id`, nullable (null for admins).
- `bookings` indexes: `(tutor_id, scheduled_date, status)`, `(child_id, scheduled_date)`,
  `(scheduled_date, status)` — replacing the ERD's single five-column index, per D-011.
- **REQ-008 partial unique index**, named `uq_booking_live_slot`:
  `CREATE UNIQUE INDEX uq_booking_live_slot ON bookings (tutor_id, scheduled_date,
  start_time) WHERE status IN ('pending','confirmed')`. In SQLAlchemy this is
  `Index(..., postgresql_where=...)`.
- Relationships navigable both ways where the ERD shows a link: parent↔children,
  child↔bookings, tutor↔{tutor_subjects, tutor_availability, exceptions, bookings},
  subject↔{tutor_subjects, bookings}, availability↔bookings, user↔tutor.
- `day_of_week` is `SMALLINT`, `0 = Monday … 6 = Sunday`. Add a check constraint
  `day_of_week BETWEEN 0 AND 6`.

`api/app/models/__init__.py` must import every model class so that a single
`import app.models` populates `Base.metadata` — Alembic autogenerate depends on this.

`api/alembic/env.py` reads the URL from `get_settings().database_url` (never from a
hardcoded `alembic.ini` value), imports `app.models`, and sets
`target_metadata = Base.metadata`. Enable `compare_type=True`.

`api/tests/test_models.py` asserts `Base.metadata` contains all nine table names and that
`uq_booking_live_slot` is present in `bookings.indexes`. Metadata-level only — no live
database required.

### Acceptance criteria

- Against an empty database: `alembic upgrade head` creates nine tables and both enums;
  `alembic downgrade base` drops everything including the enum types, leaving an empty
  schema; a second `alembic upgrade head` is idempotent.
- After upgrade, `alembic check` reports no pending autogenerate diff — models and
  migration agree.
- Inserting two `confirmed` bookings with the same `(tutor_id, scheduled_date, start_time)`
  raises `IntegrityError`; setting the first to `cancelled` then inserting succeeds.
- `uv run pytest` passes, `uv run ruff check .` is clean.
- `api/pyproject.toml` is unmodified by this task.

### Out of scope

No Pydantic schemas. No routers, no services, no CRUD helpers. No seed data, no fixtures
inserting rows, no factory library. No second migration. No changes to `docs/erd.md` — if
something in the ERD cannot be built as written, report it as spec drift and implement the
interpretation recorded in D-011.

## Verification

**Changed-risk surface:** the database schema and the service's ability to boot and reach
its two dependencies. A wrong migration is the expensive failure here because every later
phase builds on it.

**Commands, narrowest first** (all run inside the `api` container once T3.1 has landed; on
the host with `uv` otherwise):

1. `docker compose run --rm api uv run ruff check .`
2. `docker compose run --rm api uv run pytest -q`
3. `docker compose run --rm api alembic upgrade head`
4. `docker compose run --rm api alembic check`
5. `docker compose run --rm api alembic downgrade base`
6. `docker compose run --rm api alembic upgrade head` (again — idempotence)
7. `docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c '\dt'` — expect
   exactly nine tables plus `alembic_version`.
8. `docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB -c '\d bookings'` —
   confirm `uq_booking_live_slot` appears with its `WHERE` clause.

**Smoke steps:**
- `curl -s localhost:8000/health` → `{"status":"ok"}`.
- `curl -s localhost:8000/health/ready` → both `ok`.
- `docker compose stop redis`; `curl -si localhost:8000/health/ready` → `503`, body shows
  `redis` in error; `curl -s localhost:8000/health` still `{"status":"ok"}`;
  `docker compose start redis`.

**PASS requires:** REQ-002 (missing-env failure names the field), REQ-003, REQ-004, REQ-005
(both probe behaviours including the 503 case), REQ-006 (all nine tables with documented
constraints), REQ-007 (up/down/idempotent/`alembic check` clean), REQ-008 (integrity error
on duplicate live slot). Any step 3–6 failure is BLOCKED, not a warning.
