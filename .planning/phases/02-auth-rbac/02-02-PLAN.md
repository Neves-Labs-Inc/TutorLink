Phase 2 · Authentication and RBAC. Two tasks. **They are independent of each other and run
concurrently**: the auth service never imports the dependency module, and the dependency
module never imports the service. Both consume only `app.security`.

Read `.planning/CONSTITUTION.md` and `.planning/phases/02-auth-rbac/02-CONTEXT.md` first.
The frozen interfaces in `02-CONTEXT.md` are contracts, not suggestions.

relative to it. Every Python command runs **inside the `api` container**.

`P2-T2.2` is the task the whole phase exists for. `02-CONTEXT.md` records the trap it closes:

## Task P2-T2.1 — Auth service: authenticate, issue, rotate, revoke, detect reuse

**Satisfies:** REQ-020 (credential half), REQ-021 (rotation half), REQ-025, REQ-02A
**Agent:** `coder-sr`
**Dependencies:**
- `P2-T1.1` — for `hash_password` / `verify_password` / `create_access_token` /
  `create_refresh_token` / `decode_token` / `TokenError` / `DUMMY_PASSWORD_HASH` in
  `api/app/security.py`, and for the three new `Settings` fields.
- `P2-T1.2` — for the `RefreshToken` model and migration `0002`. The rotation logic writes
  and revokes rows in that table; it cannot be written against a table that does not exist.
- `P2-T1.3` — for the `db` fixture its tests are built on.

### Objective

Put every rule about credentials and refresh-token lifecycle in one service module, so the
router that follows is a thin HTTP shell and the rules are unit-testable without HTTP.

### Files owned (exclusive writable set)

```
api/app/services/auth_service.py
api/tests/test_auth_service.py
```

Two files. Do not touch `api/app/security.py`, `api/app/dependencies.py`,
`api/app/routers/`, `api/app/main.py`, `api/app/models/`, or `api/tests/conftest.py`.

### What to build

Implement exactly the four functions, three exception classes, and one dataclass frozen in
`02-CONTEXT.md`. Business rules, precisely:

**`authenticate_user(db, *, email, password) -> User`**

1. Normalise: `email.strip().lower()` (D-028). The `users.email` unique constraint is
   case-sensitive, so normalising at this boundary is what makes `Admin@X` and `admin@x` the
   same account. The seed command normalises identically, and Phase 3's `POST /api/users`
   must too.
2. Look up the user by the normalised email.
3. **When no user is found, still call `verify_password(password, DUMMY_PASSWORD_HASH)`**
   before raising. Skipping the hash on a miss makes "no such account" measurably faster than
   "wrong password" and turns the login endpoint into an account-enumeration oracle. This is
   not optional and there must be a comment saying why.
4. Raise `InvalidCredentials` when the user is missing, when `is_active` is false, or when
   the password does not verify. **One exception type for all three** — the router turns it
   into a single 401 with one message, so the response never distinguishes them.
5. Reject a password whose UTF-8 encoding exceeds 72 bytes via `password_is_encodable` before
   hashing or verifying, raising `InvalidCredentials`. bcrypt truncates silently past that
   length, which would let a 100-byte password be authenticated by its first 72 bytes.

**`issue_token_pair(db, *, user) -> IssuedTokens`**

Starts a **new family**: generate `family_id = uuid4()` and `jti = uuid4()`, mint the refresh
token from them, insert one `RefreshToken` row (`id=jti`, `family_id`, `user_id=user.id`,
`expires_at` as returned by `create_refresh_token`, `revoked_at=None`), mint the access token
from `user.role` and `user.tutor_id`, flush, and return all three values. Do not commit — the
router owns the transaction boundary.

**`rotate_refresh_token(db, *, presented) -> IssuedTokens`**

1. `decode_token(presented, expected_type=REFRESH_TOKEN_TYPE)`; any `TokenError` becomes
   `InvalidRefreshToken`.
2. Load the row by `jti`. Missing row → `InvalidRefreshToken`.
3. **`revoked_at IS NOT NULL` → this is a replay of an already-rotated token.** Revoke every
   row in the family whose `revoked_at` is `NULL` (`UPDATE refresh_tokens SET revoked_at =
   now() WHERE family_id = :fid AND revoked_at IS NULL`), then raise `RefreshTokenReused`.
   The rationale, and it must appear as a comment: either the legitimate holder replayed an
   old token, or an attacker stole one and the legitimate holder has since rotated past it.
   The two are indistinguishable from here, so the safe action is to invalidate the whole
   chain and force a fresh login. This is the standard OAuth 2.0 BCP response and it is why
   the revocation table exists at all.
4. `expires_at <= now()` → `InvalidRefreshToken` (belt and braces; `decode_token` already
   enforces `exp`, but the row is the authority on liveness).
5. Load the user; missing or `is_active` false → `InvalidRefreshToken`. This is what makes a
   deactivated account stop refreshing rather than surviving for seven days.
6. Mint a new `jti` **in the same family**, insert the new row, set the old row's
   `revoked_at = now()` and `replaced_by_id` to the new id, mint a fresh access token from
   the user's **current** `role` and `tutor_id` (re-read from the database, never carried
   over from the presented token), and return.

**`revoke_family_for_token(db, *, presented) -> None`**

Best-effort logout: decode, find the row, revoke the whole family. **Never raises** — an
absent, expired, malformed, or unknown token is a silent no-op. Logout must be idempotent and
must not tell an unauthenticated caller whether a token was valid.

All timestamps are tz-aware UTC.

**`api/tests/test_auth_service.py`** — uses the `db` fixture from `P2-T1.3` and creates its
own users with `hash_password`. Cover, at minimum:

- Correct credentials return the user; wrong password, unknown email, and an `is_active=False`
  user all raise `InvalidCredentials`, and the raised type is identical in all three cases.
- Email lookup is case- and whitespace-insensitive: `"  ADMIN@x.com "` authenticates the user
  stored as `admin@x.com`.
- A password over 72 bytes is rejected rather than truncated: hashing `"a"*80` then
  authenticating with `"a"*72` must **fail**.
- `issue_token_pair` writes exactly one row with `revoked_at IS NULL`.
- A single rotation: the new token differs, the old row is revoked, `replaced_by_id` points at
  the new row, both rows share one `family_id`, and the new access token decodes with the
  user's role.
- **Reuse detection:** issue → rotate → rotate again with the *original* token raises
  `RefreshTokenReused`, and afterwards **every** row in that family has `revoked_at` set —
  including the one that was live a moment ago. Then rotating with the most recent token also
  fails. This is the single most important test in the phase.
- Two independent logins produce two different `family_id`s, and revoking one family leaves
  the other usable. Logging out on your phone must not log you out on your laptop.
- An access token passed to `rotate_refresh_token` raises `InvalidRefreshToken`.
- `revoke_family_for_token` with `""`, with a garbage string, and with a valid token all
  return `None` without raising, and the valid one leaves the family fully revoked.

### Acceptance criteria

- `docker compose run --rm api uv run pytest -q tests/test_auth_service.py` passes, with the
  reuse-detection test present and asserting on the database rows rather than only on the
  exception.
- `docker compose run --rm api uv run ruff check .` clean.
- `grep -rn "HTTPException\|fastapi" api/app/services/auth_service.py` returns nothing — the
  service layer raises domain exceptions and knows no HTTP (constitution, layering rule).
- `grep -rn "commit()" api/app/services/auth_service.py` returns nothing — the router owns
  the transaction.
- `git diff --name-only` lists exactly the two owned files.

### Out of scope

No FastAPI, no router, no cookie handling, no status codes — `P2-T3.1` owns every one of
those. No `get_current_user` (that is `P2-T2.2`). No login rate limiting or lockout: OQ-7
defers it deliberately, and adding it here would be an unrequested feature. No Redis. No
password-reset or change-password flow. No new dependency; if one seems necessary, stop and
report.

## Task P2-T2.2 — The reusable auth dependency and the tutor-scoping helper

**Satisfies:** REQ-023, REQ-024
**Agent:** `coder-sr`
**Dependencies:**
- `P2-T1.1` — for `decode_token`, `TokenError`, and `ACCESS_TOKEN_TYPE`.
- `P2-T1.3` — for the `db` and `api` fixtures its tests are built on.

**Not** dependent on `P2-T2.1`. This task must not import `app.services.auth_service`, and it
runs concurrently with it.

### Objective

Deliver the two things Phase 3 will import on its very first line of router code: a
dependency that turns a bearer token into a typed principal, and a scoping helper that makes
"tutors see only their own data, and a cross-tutor reach returns 403" mechanical rather than
a rule each endpoint author has to remember.

### Files owned (exclusive writable set)

```
api/app/dependencies.py
api/tests/test_dependencies.py
```

Two files. `api/app/dependencies.py` is a new module and sits alongside `db.py`,
`config.py`, and `redis_client.py` — application-level wiring, not a router, not a service.

### What to build

Exactly the surface frozen in `02-CONTEXT.md`.

**`oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token", auto_error=False)`**

`auto_error=False` so this module raises its own `HTTPException` with a
`WWW-Authenticate: Bearer` header and a `{"detail": ...}` body, rather than FastAPI's default
shape. `tokenUrl` makes the Authorize button work in `/docs`.

**`get_current_user(token, db) -> CurrentUser`** — 401 for every one of: no token, malformed
token, bad signature, expired token, `typ != "access"`, no such user, `is_active` false. **One
message for all of them** (`"Could not validate credentials"`); never tell an unauthenticated
caller which of those it was.

It **does** load the `User` row on every request (D-023). One indexed primary-key lookup per
request buys the property that deactivating a user takes effect on the next request instead of
up to fifteen minutes later, which is what `is_active` soft-delete is for. Do not "optimise"
this into a claims-only path.

It returns a `CurrentUser` frozen dataclass, **never the ORM object** — the constitution
forbids an ORM instance crossing the HTTP boundary, and a frozen principal cannot be mutated
by a route by accident.

**`require_admin`** — depends on `get_current_user`, raises 403 (`"Admin privileges
required"`) when `role is not UserRole.ADMIN`. Ordering matters and falls out for free:
because it depends on `get_current_user`, an unauthenticated request gets 401, not 403.

**`Principal` / `AdminPrincipal`** — `Annotated[...]` aliases so a Phase 3 router signature is
`user: Principal` and nothing more.

**`resolve_tutor_scope(user, requested_tutor_id)`** and
**`assert_can_access_tutor(user, owner_tutor_id)`** — implement the six-row table and the
row-level rule in `02-CONTEXT.md` exactly. Both raise
`HTTPException(403, "Not permitted to access this tutor's data")` on violation.

Three points that must survive review:

- A tutor asking for *nothing in particular* gets scoped to themselves. `resolve_tutor_scope`
  returning `None` for a tutor would silently widen a list endpoint to every tutor's rows;
  it returns the caller's own `tutor_id` instead. There is no way for a tutor to opt out of
  the filter.
- A tutor account whose `users.tutor_id` is `NULL` is rejected with 403, not treated as an
  admin and not silently scoped to `NULL`. That column is nullable because admins have no
  tutor profile; a tutor row in that state is a data error and must fail loudly.
- Cross-tutor access is **403, never 404 and never an empty 200** (`CONSTITUTION.md:15`).
  Returning 404 to hide existence is a defensible pattern in general and is explicitly *not*
  what this project does; do not substitute it.

Write module docstrings that state all of the above, because Phase 3's authors will read this
file rather than this plan.

**`api/tests/test_dependencies.py`** — this is the "exercised" half of the deliverable, and it
is why the task exists separately. Build a **throwaway FastAPI app inside the test module**
with probe routes such as `/probe/any` (`Principal`), `/probe/admin` (`AdminPrincipal`), and
`/probe/tutors/{tutor_id}` (calls `resolve_tutor_scope`). Mount it on a `TestClient` with
`get_db` overridden to the `db` fixture.

**These probe routes exist only in the test module and are never added to `app.main`.**
Phase 2 ships no `/api/*` endpoint; see the REQ-024 amendment in `REQUIREMENTS.md`.

Cover the full matrix:

| Case | Expected |
|---|---|
| No `Authorization` header | 401, `WWW-Authenticate: Bearer` present |
| `Authorization: Bearer garbage` | 401 |
| A **refresh**-type token | 401 — proves `typ` is enforced at the dependency, not only in `decode_token` |
| An expired access token | 401 |
| A valid token for a user that was then deleted | 401 |
| A valid token for a user whose `is_active` was set false after the token was minted | 401 — the D-023 property |
| Admin token on `/probe/any` and `/probe/admin` | 200, 200 |
| Tutor token on `/probe/admin` | **403** |
| Tutor token, own `tutor_id` in the path | 200, scope equals own id |
| Tutor token, **another** tutor's id in the path | **403** — and the body is `{"detail": ...}`, not an empty 200 |
| Tutor token, no id supplied | 200, and the resolved scope is the caller's own `tutor_id` |
| Tutor token whose `users.tutor_id` is `NULL` | **403** |
| Admin token, no id supplied | 200, resolved scope is `None` |
| Admin token, another tutor's id | 200, resolved scope is that id unchanged |

Every 401 and 403 body must be a `{"detail": "<string>"}` object.

### Acceptance criteria

- `docker compose run --rm api uv run pytest -q tests/test_dependencies.py` passes with every
  row of the matrix present as a distinct assertion.
- `docker compose run --rm api uv run ruff check .` clean.
- `grep -rn "auth_service" api/app/dependencies.py` returns nothing — no coupling to
  `P2-T2.1`.
- `grep -rn "probe" api/app/` returns nothing — the probe routes never leave the test module.
- `git diff --name-only` lists exactly the two owned files.
- `api/app/main.py` is unchanged by this task.

### Out of scope

No `/auth` routes and no `main.py` edit — `P2-T3.1` owns both. No permission or policy
framework, no decorator DSL, no role hierarchy: there are exactly two roles and a
`require_admin` covers the whole matrix in `docs/api-design.md:95-107`. No caching of the
user lookup (no Redis, no `lru_cache` on a per-request lookup — that would reintroduce
precisely the staleness D-023 exists to remove). No `/api/*` endpoint of any kind, not even a
trivial one to demonstrate the dependency.

## Verification

**Changed-risk surface.** This plan is where the phase's security properties actually live.
Two failure modes matter more than the rest, and both are silent:

1. **A scoping helper that returns an empty result instead of a 403.** An endpoint that
   returns `200 []` for a cross-tutor request looks fine in a browser and leaks the fact that
   the caller's filter was applied rather than their access denied — and worse, one careless
   Phase 3 endpoint that forgets to apply the returned scope then leaks rows.
2. **Refresh-token reuse that is not detected.** A stolen refresh token stays valid for seven
   days and rotates itself indefinitely. The only thing standing between that and the system
   is the `revoked_at IS NOT NULL` branch in `rotate_refresh_token`.

**Commands, narrowest first** (stack up; all in-container):

1. `docker compose run --rm api uv run ruff check .`
2. `docker compose run --rm api uv run pytest -q tests/test_auth_service.py`
3. `docker compose run --rm api uv run pytest -q tests/test_dependencies.py`
4. `docker compose run --rm api uv run pytest -q` — the whole suite, Phase 1 tests included
5. `grep -rn "fastapi\|HTTPException" api/app/services/auth_service.py` → empty
6. `grep -rn "auth_service" api/app/dependencies.py` → empty
7. `grep -rn "probe" api/app/` → empty

**Targeted repro for the two failure modes** — read the test output, do not just trust the
exit code:

- In `test_auth_service.py`, the reuse test must assert on **rows**: after the replay,
  `SELECT count(*) FROM refresh_tokens WHERE family_id = :fid AND revoked_at IS NULL` is `0`.
  A test that only asserts `pytest.raises(RefreshTokenReused)` passes even if the family was
  never revoked, and is not sufficient.
- In `test_dependencies.py`, the cross-tutor case must assert `response.status_code == 403`
  **and** `response.json() == {"detail": ...}`. A test asserting only `!= 200` would pass on
  a 404 and is not sufficient.

**PASS requires:**

- **REQ-020** — valid credentials authenticate; invalid credentials, unknown accounts, and
  inactive accounts are indistinguishable from each other at the service boundary.
- **REQ-021** — a valid refresh token rotates to a new pair; an expired, malformed, or
  wrong-type token is rejected.
- **REQ-023** — a missing or invalid bearer token yields 401 with `WWW-Authenticate: Bearer`,
  proven against real probe routes rather than by inspection.
- **REQ-024** — every row of the scoping matrix, with 403 (not 404, not empty 200) on every
  cross-tutor path.
- **REQ-02A** — reuse of a rotated refresh token revokes the entire family, proven by row
  count, and independent login families are unaffected.

A missing or weakened reuse-detection test is **BLOCKED**, not a warning. So is any
cross-tutor case that yields anything other than 403.
