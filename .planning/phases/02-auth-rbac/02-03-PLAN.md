## Task P2-T3.1 — `/auth` router, refresh cookie, and the uniform error envelope

**Satisfies:** REQ-020, REQ-021, REQ-029, REQ-02A (the logout endpoint)
**Agent:** `coder-sr`
**Dependencies:**
- `P2-T2.1` — for `authenticate_user`, `issue_token_pair`, `rotate_refresh_token`,
  `revoke_family_for_token`, `IssuedTokens`, and the three exception classes in
  `api/app/services/auth_service.py`. The router is a shell over those; it cannot be written
  first.
- `P2-T1.1` — for `TokenPair` / `RefreshRequest` in `api/app/schemas/auth.py` and for
  `python-multipart`, without which `OAuth2PasswordRequestForm` fails at import.
- `P2-T1.3` — for the `api` fixture its tests use.

### Objective

Expose the three auth endpoints exactly as `docs/api-design.md` and D-015 specify, manage the
refresh cookie, and make every error in the application come back as `{"detail": "<string>"}`
with the status codes the design document lists.

### Files owned (exclusive writable set)

```
api/app/routers/auth.py
api/app/main.py
api/tests/test_auth_routes.py
```

Three files. `api/app/main.py` is shared with nothing else in this phase — no other Phase 2
task may edit it, which is why the router registration and the exception handlers are one
task rather than two.

### What to build

**`api/app/routers/auth.py`** — `APIRouter(prefix="/auth", tags=["auth"])`. Routers do HTTP,
auth, and `Depends(get_db)` only; every rule lives in the service (constitution).

**`POST /auth/token`** — takes `form_data: Annotated[OAuth2PasswordRequestForm, Depends()]`.
This is **form-encoded**, not JSON (D-021): `docs/api-design.md:16,27` says "standard OAuth2
password flow, implemented natively via FastAPI's `OAuth2PasswordBearer`", and the standard
flow is `application/x-www-form-urlencoded`. The JSON block at `docs/api-design.md:29-35`
names the fields, not the media type — the same reading D-002 applied to that document's
`.jsx` filenames.

Calls `authenticate_user`, then `issue_token_pair`, then **commits**, then sets the cookie and
returns `TokenPair`. `InvalidCredentials` → `HTTPException(401, "Incorrect email or
password", headers={"WWW-Authenticate": "Bearer"})`.

The refresh token appears in **both** the cookie and the response body (D-015). The body is
what `docs/api-design.md:37-44` promises and is what non-browser clients use; the cookie is
what `docs/admin-dashboard-design.md:24,34` promises and is what the dashboard uses. Neither
document has to change.

**`POST /auth/refresh`** — reads the token from, in order:

1. `refresh_token: Annotated[str | None, Cookie()] = None`
2. the optional JSON body `RefreshRequest`, declared with a default so a request with **no
   body at all** is valid — the browser sends none

Neither present → `HTTPException(401, "Invalid refresh token")`. Calls
`rotate_refresh_token`, commits, sets the **new** cookie, returns `TokenPair`.

Both `InvalidRefreshToken` and `RefreshTokenReused` map to the **same** 401 with the **same**
message. Do not add a distinct message, status, or header for reuse: telling an attacker that
their stolen token was detected as a replay tells them the family has been burned. The family
revocation already happened inside the service; the response says nothing about it. Note that
`RefreshTokenReused` subclasses `InvalidRefreshToken`, so one `except` clause covers both —
but catch them in the right order if you catch them separately.

Returning `refresh_token` in the `/auth/refresh` response body is an **addition** to
`docs/api-design.md:57-63`, which shows only `access_token` and `token_type`. It is required:
rotation issues a new refresh token, and a non-browser client that cannot see the cookie must
receive it somewhere. The addition is purely additive and breaks no documented client. It is
recorded as spec drift in `STATE.md`; **do not edit `docs/`.**

**`POST /auth/logout`** — reads the token by the same cookie-then-body rule, calls
`revoke_family_for_token`, commits, deletes the cookie, and returns **204 No Content** in
every case, including when no token was supplied and when the token was garbage. Logout is
idempotent and reveals nothing.

`POST /auth/logout` is **not** in `docs/api-design.md`. It is introduced by REQ-02A, because
a revocation store that no client can trigger is decoration. Recorded as spec drift.

**Cookie attributes — one helper, used by all three endpoints so they cannot drift apart:**

```
key="refresh_token", httponly=True, samesite="lax", path="/auth",
secure=not get_settings().debug, max_age=<refresh_token_expire_days as seconds>
```

`Secure` is derived from `debug` rather than from a new environment variable (D-027):
`.env.example` ships `DEBUG=true` for local HTTP and production sets it false, so the flag is
already exactly the signal needed. **Deletion must repeat `path` and `samesite` identically**
or the browser will not match the cookie and logout will leave it in place. `SameSite=Lax`
is what makes these POSTs CSRF-safe; do not change it to `None` (D-012).

**`api/app/main.py`** — three changes and nothing else:

1. `app.include_router(auth.router)`.
2. A `RequestValidationError` handler returning **400**, not FastAPI's default 422, with
   `{"detail": "<single human-readable string>"}` rather than the default list of error
   objects. `docs/api-design.md:637-644` lists 400 for validation and does not list 422 at
   all, and REQ-029 requires the documented codes. Compose the string from the first error's
   location and message.
3. A `StarletteHTTPException` handler is **not** needed — FastAPI already renders
   `HTTPException` as `{"detail": ...}`. Do not add one.

Leave the `# No CORS middleware by design (D-012)` comment at `main.py:7` exactly where it is.

**`api/tests/test_auth_routes.py`** — uses the `api` and `db` fixtures. Cover:

- `POST /auth/token` with form-encoded good credentials → 200, body has `access_token`,
  `refresh_token`, `token_type == "bearer"`; response carries a `Set-Cookie` for
  `refresh_token` containing `HttpOnly`, `SameSite=Lax`, and `Path=/auth`.
- Bad password, unknown email, and an inactive user → 401, all three with the **same** body
  and `WWW-Authenticate: Bearer`.
- A JSON body posted to `/auth/token` → 400 (the remapped validation error), and the body is
  `{"detail": "<string>"}` — assert `isinstance(body["detail"], str)`, which is what proves
  the 422-to-400 remap actually ran.
- `POST /auth/refresh` with the cookie carried by the TestClient → 200 and a **different**
  refresh token than the one presented.
- `POST /auth/refresh` with a JSON body and no cookie → 200 (the non-browser path).
- `POST /auth/refresh` with neither → 401.
- **Replay:** login → refresh → refresh again with the *first* refresh token → 401, and the
  token issued by the successful refresh now also fails with 401. End to end through HTTP,
  not only at the service layer.
- `POST /auth/logout` → 204 with a cookie-clearing `Set-Cookie`; the refresh token then fails
  with 401. Logging out twice is still 204.
- `POST /auth/logout` with no cookie and no body → 204.

## Task P2-T3.2 — Idempotent first-admin seed command

**Satisfies:** REQ-026, REQ-025
**Agent:** `coder-jr`
**Dependencies:**
- `P2-T1.1` — for `hash_password` and `password_is_encodable`.
- `P2-T1.3` — for the `db` fixture its test uses.

**Not** dependent on `P2-T2.1`, `P2-T2.2`, or `P2-T3.1`. It writes a `users` row directly and
touches no auth service, no dependency, and no router.

### Objective

Make the system loginable. Without this, a correct auth stack has nobody to authenticate.

### Files owned (exclusive writable set)

```
api/app/cli.py
api/tests/test_cli_seed.py
```

Two files, both new. Do not edit `docker/api.Dockerfile`, `docker-compose.yml`,
`.env.example`, `Readme.md`, or `api/pyproject.toml`.

### What to build

**`api/app/cli.py`** — invoked as
`docker compose run --rm api python -m app.cli seed-admin`. Use `argparse` from the standard
library. **Do not add `typer` or `click`**: one subcommand does not justify a runtime
dependency, and the constitution forbids adding one that is not recorded.

Credential sourcing, in this order:

1. `TUTORLINK_ADMIN_EMAIL` and `TUTORLINK_ADMIN_PASSWORD` from the process environment.
2. Whichever is absent is prompted for interactively — `input()` for the email,
   `getpass.getpass()` for the password, **prompted twice and compared**. When stdin is not a
   TTY and a value is missing, exit `2` with a message naming the missing variable rather
   than hanging on a prompt.

These two variables are **command inputs, not `Settings` fields.** Read them with
`os.environ.get`, do not add them to `Settings`, and do not add them to `.env.example` — they
are one-shot bootstrap credentials and a committed example file is the wrong place for the
shape of a real admin password (constitution: secrets come only from env; never commit them).

Behaviour:

- Normalise the email with `.strip().lower()`, identically to `authenticate_user` (D-028).
- Validate: non-empty email containing `@`; password at least 8 characters (matching the
  dashboard's client-side rule at `dashboard/src/pages/Login.tsx:26`) and
  `password_is_encodable`. Failure → exit `2` with a message. **Never echo the password.**
- **Idempotent (D-018):** if a user with that email already exists, print
  `admin already exists: <email> (no change)` and exit `0`. Do **not** create a duplicate, do
  **not** reset the password, do **not** flip `is_active`. Re-running the command must be a
  safe no-op — that is the whole point, since it will be run by anyone following the Readme.
- Otherwise insert `role=UserRole.ADMIN`, `tutor_id=None`, `is_active=True`,
  `hashed_password=hash_password(password)`, commit, print
  `created admin: <email>`, exit `0`.
- Open the session with `SessionLocal()` from `app.db` in a `try/finally`. Do **not** use
  `get_db()` — that is a FastAPI dependency generator and is the wrong tool outside a request.

Exit codes: `0` created or already present, `2` bad input. Print the email; never print,
log, or echo the password or the hash.

**`api/tests/test_cli_seed.py`** — uses the `db` fixture. Call the seed function directly
with an injected session rather than shelling out, so structure `cli.py` as
`seed_admin(db, *, email, password) -> str` (returning `"created"` or `"exists"`) with the
argparse/`main()` layer on top doing only I/O. Cover: a fresh database creates exactly one
admin whose password verifies; a second call with the same email creates nothing and returns
`"exists"`; a second call with the same email and a **different** password leaves the original
hash untouched; email is normalised, so `"  ADMIN@X.COM "` and `"admin@x.com"` are the same
account; a short password and an over-72-byte password are both rejected.

### Acceptance criteria

- `docker compose run --rm -e TUTORLINK_ADMIN_EMAIL=admin@tutorlink.test -e TUTORLINK_ADMIN_PASSWORD=change-me-please api python -m app.cli seed-admin`
  prints `created admin: admin@tutorlink.test` and exits `0`.
- Running the identical command again prints `admin already exists` and exits `0`, and
  `SELECT count(*) FROM users` is still `1`.
- Running it again with a **different** password leaves `hashed_password` byte-identical
  (capture it with `psql` before and after).
- `SELECT role, tutor_id, is_active FROM users` → `admin`, `NULL`, `true`.
- With both variables unset and stdin not a TTY, the command exits `2` naming the missing
  variable — it does not hang.
- `docker compose run --rm api uv run pytest -q tests/test_cli_seed.py` passes.
- `docker compose run --rm api uv run ruff check .` clean.
- `grep -rn "TUTORLINK_ADMIN" .env.example Readme.md docker-compose.yml` returns nothing.
- `git diff --name-only` lists exactly the two owned files.

### Out of scope

**No HTTP setup endpoint, no registration route, no "create first admin if none exists" hook
on startup — not now, not ever (D-018).** No seeding of tutors, subjects, parents, children,
or bookings; the database stays otherwise empty. No password-reset subcommand. No
`--force`/`--reset-password` flag: a command that can silently reset an admin password is
exactly the thing idempotency is protecting against; if that is ever wanted it is a separate
REQ. No new dependency. No Dockerfile `ENTRYPOINT` change.

## Verification

**Changed-risk surface.** The HTTP boundary of the entire authentication system, plus the one
command that puts a credential into the database. Three failure modes to hunt:

1. A cookie whose attributes do not match between set and delete, so logout appears to work
   while the browser keeps sending a revoked token.
2. The 422-to-400 remap silently not firing, leaving a list-shaped `detail` that REQ-029
   forbids and that the dashboard's error rendering will not handle.
3. A seed command that resets an existing admin's password on a re-run — data loss dressed
   up as convenience.

**Commands, narrowest first** (stack up, migrations applied; all in-container):

1. `docker compose run --rm api uv run ruff check .`
2. `docker compose run --rm api uv run pytest -q tests/test_cli_seed.py`
3. `docker compose run --rm api uv run pytest -q tests/test_auth_routes.py`
4. `docker compose run --rm api uv run pytest -q`
5. `curl -s localhost:8000/openapi.json | grep -c '"/api/'` → `0`

**End-to-end smoke — run it in this order, it is the phase's backend acceptance:**

```
# 1. seed
docker compose run --rm -e TUTORLINK_ADMIN_EMAIL=admin@tutorlink.test \
  -e TUTORLINK_ADMIN_PASSWORD=change-me-please api python -m app.cli seed-admin
# 2. idempotence — expect "already exists", and count(*) still 1
docker compose run --rm -e TUTORLINK_ADMIN_EMAIL=admin@tutorlink.test \
  -e TUTORLINK_ADMIN_PASSWORD=totally-different api python -m app.cli seed-admin
docker compose exec postgres psql -U $POSTGRES_USER -d $POSTGRES_DB \
  -c 'select count(*), role, is_active from users group by role, is_active'
# 3. login — form-encoded, cookie jar on
curl -s -c /tmp/tl.jar -i -X POST localhost:8000/auth/token \
  -d 'username=admin@tutorlink.test&password=change-me-please'
# 4. wrong password
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8000/auth/token \
  -d 'username=admin@tutorlink.test&password=wrong'            # expect 401
# 5. refresh via cookie
curl -s -b /tmp/tl.jar -c /tmp/tl.jar -X POST localhost:8000/auth/refresh
# 6. REPLAY the first refresh token by body
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8000/auth/refresh \
  -H 'Content-Type: application/json' -d '{"refresh_token":"<the FIRST one>"}'   # expect 401
# 7. the token from step 5 must now ALSO fail — the family was burned
curl -s -o /dev/null -w '%{http_code}\n' -b /tmp/tl.jar -X POST localhost:8000/auth/refresh
# expect 401
# 8. log in again, then logout, then refresh
curl -s -c /tmp/tl2.jar -X POST localhost:8000/auth/token \
  -d 'username=admin@tutorlink.test&password=change-me-please'
curl -s -o /dev/null -w '%{http_code}\n' -b /tmp/tl2.jar -c /tmp/tl2.jar -X POST localhost:8000/auth/logout
# expect 204
curl -s -o /dev/null -w '%{http_code}\n' -b /tmp/tl2.jar -X POST localhost:8000/auth/refresh
# expect 401
# 9. validation envelope
curl -s -X POST localhost:8000/auth/token -H 'Content-Type: application/json' -d '{}' | head -c 200
# expect HTTP 400 and {"detail":"<string>"} — a LIST-shaped detail is a FAIL
```

Step 3's headers must contain `Set-Cookie: refresh_token=…; HttpOnly; Path=/auth; SameSite=Lax`
and, because `DEBUG=true` locally, **no** `Secure` flag. Step 8's logout `Set-Cookie` must
carry the same `Path=/auth` and `SameSite=Lax`.

**PASS requires:**

- **REQ-020** — step 3 returns all three fields plus the cookie; step 4 is 401.
- **REQ-021** — step 5 rotates; step 9's malformed request is 400 with a string detail.
- **REQ-026** — step 1 creates exactly one admin; step 2 changes nothing and the password
  hash is untouched.
- **REQ-029** — every error body in every step above is `{"detail": "<string>"}`, and the
  status codes are drawn only from 400/401/403/404/409.
- **REQ-02A** — steps 6, 7, and 8 all behave as annotated. **Step 7 is the gate**: if the
  token issued in step 5 still works after the replay in step 6, family revocation is not
  wired and the plan is BLOCKED, not passed with a note.
