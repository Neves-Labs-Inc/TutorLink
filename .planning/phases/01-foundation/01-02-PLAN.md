**`src/lib/api.ts`** — one Axios instance, the only HTTP entry point in the app.

interceptor that currently only re-throws — leave a `// Phase 2: silent refresh on 401`
marker. Do not implement refresh logic now.

**`src/lib/queryClient.ts`** — a `QueryClient` with `retry: 1` and
`refetchOnWindowFocus: false`.

**`src/stores/authStore.ts`** — Zustand store, shape only:
`{ accessToken: string | null, role: 'admin' | 'tutor' | null, tutorId: string | null,
setSession(...), clearSession() }`. Initial state is all `null`. **The access token lives
in memory only** — no `localStorage`, no `sessionStorage`, no Zustand `persist`
middleware. Not now, not ever.

**`src/stores/uiStore.ts`** — `{ mobileNavOpen: boolean, toggleMobileNav(), closeMobileNav() }`.
T2.2 consumes this for the hamburger menu.

**`src/components/layout/RouteGuard.tsx`** — reads `role` from `authStore`. Accepts an
`allow: ('admin' | 'tutor')[]` prop. `role === null` → `<Navigate to="/login" replace />`;
role not in `allow` → redirect to `/dashboard` for admin, `/schedule` for tutor. Because
`role` is always `null` in Phase 1, every protected route redirects to `/login` — that is
the correct Phase 1 behaviour, not a bug.

**`src/components/layout/AppShell.tsx`** — create it now as a **pass-through stub**:
accepts `children` and renders them inside a single `<div>`. T2.2 replaces its body. Doing
it this way keeps `App.tsx` exclusively yours.

**`src/App.tsx`** — `BrowserRouter` with these routes:

| Path | Element |
|---|---|
| `/login` | `<Login />` — outside `AppShell` |
| `/dashboard` | `<RouteGuard allow={['admin']}><AppShell><Dashboard /></AppShell></RouteGuard>` |
| `/schedule` | `<RouteGuard allow={['tutor']}><AppShell><Schedule /></AppShell></RouteGuard>` |
| `/` | redirect to `/login` |
| `*` | `<NotFound />` |

**`src/main.tsx`** — mount `<QueryClientProvider client={queryClient}><App /></QueryClientProvider>`
in `React.StrictMode`.

**Pages** — each renders a single heading and nothing else. `Login.tsx` renders an
unstyled `<form>` with email and password inputs and a submit button whose `onSubmit`
calls `preventDefault()` and does nothing further. T2.2 will rewrite it.

**`.env.example`** — `VITE_API_BASE_URL=` and `VITE_API_PROXY_TARGET=http://localhost:8000`,
with a comment that Compose overrides the proxy target to `http://api:8000`.

### What to build

**1. `RouteGuard.tsx` — short-circuit the null-role redirect in dev.**

Read `accessToken` as well as `role` from `authStore` (two separate primitive selectors —
do not return a new object from one selector). Inside the existing `role === null` branch,
return `children` instead of `<Navigate to="/login" replace />` when the dev gate is open:

```tsx
// Dev-only escape hatch (STATE.md D-013). Phase 1 ships no auth, so `role` is always
// null and every protected route would otherwise redirect to /login, making the shell
// impossible to inspect. `import.meta.env.DEV` is statically replaced with `false` by
// `vite build`, so this branch is dead-code-eliminated from every production bundle.
// Narrow or remove in Phase 2 when real login lands — see the note at the end of this task.
const devNoAuth = import.meta.env.DEV && accessToken === null

if (role === null) {
  if (devNoAuth) {
    return children
  }
  return <Navigate to="/login" replace />
}
```

The role-mismatch branch below it is untouched and keeps redirecting.

**What the gate means, precisely.** Two conditions, both required:

- `import.meta.env.DEV` — Vite's built-in boolean. It is `true` under `vite dev` and
  statically `false` under `vite build`. It is already typed: `dashboard/src/vite-env.d.ts`
  declares a local `ImportMetaEnv`, which merges with the one from `vite/client`, and that
  is where `DEV` comes from. **Do not add `DEV` to `vite-env.d.ts`** — the file is outside
  this task's writable set and the declaration is unnecessary.
- `accessToken === null` — the operational reading of "no auth is configured". In Phase 1
  this is trivially always true, because nothing ever calls `setSession`. It is written
  anyway because it is what makes the bypass self-limiting in Phase 2: the moment a real
  login issues a token, the bypass goes inert *even in dev*, so a developer can exercise
  the genuine login flow locally without deleting anything.

**Do not introduce an environment variable for this.** No `VITE_DEV_AUTH_BYPASS` or
similar. Neither `.env.example` declares one, adding one would mean editing two files owned
by other tasks, and a runtime env var is strictly worse than `import.meta.env.DEV` because
it survives into the production bundle instead of being compiled away.

**2. `AppShell.tsx` — select the chrome from the route while `role` is null.**

`AppShell` currently reads `role` and falls back to the admin chrome when it is `null`.
With the bypass, `role` is still `null` on both routes, so `/schedule` would render
`AdminSidebar` and `TutorNav` would remain unreachable — which is exactly the omission that
made REQ-010 unverifiable in the first place. Derive the fallback from the current path
instead, gated so it too is compiled out:

```tsx
const { pathname } = useLocation()   // from 'react-router-dom'; AppShell renders inside <Routes>
// Dev-only companion to the RouteGuard bypass (D-013): with no session, pick the chrome
// from the route so /schedule exercises TutorNav and /dashboard exercises AdminSidebar.
const isTutor =
  role === 'tutor' ||
  (import.meta.env.DEV && role === null && pathname.startsWith('/schedule'))
```

Update the existing `// Phase 1 has no auth…` comment to describe this, keeping the
reference to D-013. Everything else in the file — the flex layout, `max-w-6xl` main region,
the `pb-[calc(5.5rem+env(safe-area-inset-bottom))]` tutor padding, all class names — stays
byte-identical. This is a logic change, not a visual one.

**Why the route, and not a query param or a `/dev/*` route.** A query param (`?role=tutor`)
is a second thing QA has to remember and does not survive an in-app navigation; a `/dev/*`
route means editing `App.tsx` and still leaves `AppShell` reading a null `role`, so it
solves nothing on its own. Seeding a fake role into `authStore` was also rejected: it means
writing store state from a render or an effect, it makes the two shells stick to whichever
was loaded first, and it puts pretend-auth into the store that Phase 2 has to unpick. The
route already carries the role intent — `/dashboard` is admin, `/schedule` is tutor — so
reading it is both the smallest change and the one with nothing to remember.

## Verification

**Changed-risk surface:** the frontend build pipeline, the responsive shell, and — new with
T2.3 — the route guard, which is the one piece of this plan whose failure mode is a
*security* one rather than a cosmetic one. The likely failures are a broken Tailwind/shadcn
setup, a proxy that does not resolve from inside the container, mobile layout overflow,
and a dev bypass that survives into a production build.

**Commands, narrowest first:**

1. `docker compose run --rm dashboard npx tsc -b` — **not** `tsc --noEmit`. The root
   `tsconfig.json` is a solution file with `"files": []`, so bare `tsc --noEmit` type-checks
   zero files and exits 0 regardless of the code. `tsc -b` follows the project references
   and is the real gate. Treat a green `tsc --noEmit` as no evidence at all.
2. `docker compose run --rm dashboard npm run lint`
3. `docker compose run --rm dashboard npm run build`
4. `grep -ri "localstorage\|sessionstorage" dashboard/src` → no matches
5. `grep -r "import.meta.env.DEV" dashboard/dist` → no matches (proves T2.3's bypass was
   eliminated from the production bundle)
6. `git -C . status --porcelain dashboard` → no untracked build output (`dist/`,
   `node_modules/` must be ignored)

**Smoke steps — dev server** (`npm run dev`, stack up). The two shell URLs are fixed:
`/dashboard` is the **admin** shell, `/schedule` is the **tutor** shell. There is no other
