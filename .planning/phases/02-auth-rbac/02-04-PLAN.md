## Task P2-T4.1 — Auth client core: token decoding, interceptors, silent refresh, bootstrap

**Satisfies:** REQ-027
**Agent:** `coder-sr`
**Dependencies:** none — dispatchable immediately against the frozen HTTP contract.

### Objective

Build the layer that owns the access token: attach it to requests, refresh it silently when
it expires, restore the session on page load from the HttpOnly cookie, and drop everything on
logout. No UI.

### Files owned (exclusive writable set)

```
dashboard/src/lib/auth.ts                    (new)
dashboard/src/lib/api.ts                     (rewrites the Phase 1 stub interceptor)
dashboard/src/stores/authStore.ts
dashboard/src/hooks/useAuth.ts               (new)
dashboard/src/components/auth/AuthProvider.tsx   (new)
dashboard/src/App.tsx
```

Do not touch `Login.tsx`, `RouteGuard.tsx`, `AppShell.tsx`, `AdminSidebar.tsx`, `TutorNav.tsx`,
`index.css`, `main.tsx`, `queryClient.ts`, `uiStore.ts`, `vite.config.ts`, `package.json`, or
anything under `components/ui/`. Three other tasks own those and run concurrently.

### What to build

**`src/lib/auth.ts` — pure token handling, no HTTP, no React.**

`decodeAccessToken(token: string): { sub: string; role: 'admin' | 'tutor'; tutorId: string | null; exp: number } | null`

Split on `.`, base64url-decode the payload segment (`atob` after replacing `-`/`_` and
padding), `JSON.parse`, validate that `sub`, `role`, and `exp` are present and that `role` is
one of the two literals, and return `null` on any failure rather than throwing.

`docs/admin-dashboard-design.md:36` says the role is read from the decoded JWT, so this is the
documented design and not an invention. **Add no dependency for it** — no `jwt-decode`, no
`jose`. It is fifteen lines and the constitution forbids an unrecorded runtime dependency.

Write a comment saying, in so many words: *this decode is not verification.* The signature is
never checked in the browser and must never be trusted for authorisation. It reads the role
only so the UI can pick which chrome to render; every actual access decision is the server's,
and the server re-verifies on every request.

**`src/stores/authStore.ts` — add the session status.**

Keep the existing fields and the "memory only, no web storage, not now, not ever" comment
verbatim. Add `status: AuthStatus` per the frozen shape in `02-CONTEXT.md`, initialised to
`'loading'`. Change `setSession` to take `{ accessToken }` alone and derive `role`/`tutorId`
by calling `decodeAccessToken` — one source of truth for the session, so the store cannot
disagree with the token. `setSession` sets `status: 'authenticated'`; `clearSession` resets
everything and sets `status: 'anonymous'`. A token that fails to decode must land in the
`clearSession` state, never in a half-authenticated one.

**No `localStorage`, no `sessionStorage`, no Zustand `persist`.** The refresh cookie is the
only thing that survives a reload, and it is HttpOnly on purpose.

**`src/lib/api.ts` — two Axios instances and the interceptors.**

Export both from this file so that `src/lib/api.ts` remains the only module in `src/` that
imports `axios` (REQ-009's acceptance criterion, and it still holds):

- `api` — the instance every future `/api/*` call uses. Keeps `baseURL:
  import.meta.env.VITE_API_BASE_URL ?? ''` and `withCredentials: true` exactly as Phase 1 set
  them.
- `authApi` — same config, **no interceptors**, used only for `/auth/token`, `/auth/refresh`,
  and `/auth/logout`. It exists so a refresh triggered by a 401 cannot itself be intercepted
  and retried into an infinite loop.

Request interceptor on `api`: attach `Authorization: Bearer ${accessToken}` read via
`useAuthStore.getState()`, skipping when there is no token.

Response interceptor on `api`: on a `401` for a request that has not already been retried,
await `refreshSession()`, then replay the original request once with the new token. Mark the
replay on the request config so a second 401 rejects instead of looping. Any other status
re-throws unchanged.

`refreshSession(): Promise<string>` — **single-flight**. A module-level
`let refreshPromise: Promise<string> | null = null`; concurrent callers await the same
promise; it is cleared in a `finally`. On success it calls `setSession` and resolves the new
access token; on failure it calls `clearSession` and rejects.

Single-flight is not an optimisation here, it is a correctness requirement. Refresh tokens
**rotate** (D-017): the second of two concurrent refreshes would present a token the first one
has already rotated away, the server would read that as a replay, and it would revoke the
entire family — logging the user out instantly. Two parallel API calls both 401-ing on an
expired access token is the ordinary case, not an edge case.

Also export thin request helpers used by the hook:

- `requestLogin(email, password)` — `authApi.post('/auth/token', new URLSearchParams({username: email, password}))`.
  **Form-encoded, not JSON** (D-021): `username`, not `email`. Sending JSON returns 400.
  The response body contains `refresh_token`; **ignore it and never store it.** The browser's
  copy is the HttpOnly cookie the server set.
- `requestRefresh()` — `authApi.post('/auth/refresh')` with **no body**; the cookie carries it.
- `requestLogout()` — `authApi.post('/auth/logout')`; treat any error as success, since the
  server returns 204 unconditionally and a failed logout must still clear the client.

**`src/hooks/useAuth.ts`** — the frozen shape. `login` and `logout` are TanStack Query
`useMutation`s over the helpers above. `logout` must, in order: call `requestLogout()`, call
`clearSession()`, call `queryClient.clear()`, and navigate to `/login` with `replace: true`.
Clearing the query cache is not optional — without it the next user to log in on the same tab
sees the previous user's cached rows, which is a data-leak bug that will not surface until
Phase 5 has data to cache.

`login` on success calls `setSession({ accessToken })` and navigates by role: `admin` →
`/dashboard`, `tutor` → `/schedule` (`docs/admin-dashboard-design.md:35`). Expose
`loginError` so the page can render the server's `detail` string.

**`src/components/auth/AuthProvider.tsx`** — runs the bootstrap exactly once on mount:
call `refreshSession()`; on rejection the store is already `'anonymous'`, which is the correct
resting state for a first-time visitor. Renders `children` unconditionally — it gates nothing;
`RouteGuard` reads `status`.

Guard the effect with a **module-level** `let bootstrapStarted = false`, not only a `useRef`.
`main.tsx` renders inside `<React.StrictMode>`, which deliberately double-invokes effects in
development. Two bootstrap refreshes with the same cookie means the second presents a rotated
token, the server treats it as a replay, and the family is revoked — you are logged out the
instant you load the page, in dev only, and it looks like a backend bug. The single-flight
promise in `refreshSession` already covers the overlapping case; the module flag covers the
sequential one. Keep both, and comment why.

**`src/App.tsx`** — wrap the existing `<Routes>` in `<AuthProvider>`, inside `<BrowserRouter>`
so the hook can navigate. Change nothing else: no route added, removed, or reordered.

- `grep -rin "localstorage\|sessionstorage\|persist(" dashboard/src` → no matches.
- `grep -rn "from 'axios'\|from \"axios\"" dashboard/src` → matches only `src/lib/api.ts`.

### Out of scope

No UI, no styling, no shadcn component, no change to any page or layout component. No
`/api/*` call — there is no `/api/*` endpoint to call. No token stored anywhere but memory.
No route change. No test runner (D-026: Phase 2 adds none; the gate is `tsc -b` + lint +

## Task P2-T4.2 — Login page wired to `POST /auth/token`

**Satisfies:** REQ-027
**Agent:** `coder-jr`
**Dependencies:** `P2-T4.1`, for `useAuth()` in `dashboard/src/hooks/useAuth.ts` — the page
calls `login` and renders `loginError`, and neither exists before that task lands.

### Objective

Turn the existing presentation-only login card into a real sign-in, changing as little of it
as possible.

### Files owned (exclusive writable set)

```
dashboard/src/pages/Login.tsx
```

One file. `Login.tsx` already implements the four visual states REQ-010 asked for; this task
replaces its fake submit with the real one and adds one form-level error region. Do not touch
`index.css`, any `components/ui/` file, `AppShell.tsx`, or the stores.

### What to build

Replace the `setTimeout` placeholder at `Login.tsx:37-39` with `useAuth().login(...)`.

- Keep the existing client-side `validate()` exactly as it is, including the 8-character
  minimum, and keep it running **before** the request. Keep every existing class name,
  `aria-invalid`, `aria-describedby`, and `role="alert"` attribute — they were built for
  REQ-010 and REQ-010 is still unverified in a browser, so do not perturb them.
- Drive `disabled` from `isLoggingIn` instead of the local `submitting` state, so the existing
  disabled styling now reflects a real in-flight request.
- Add **one** form-level error region above the submit button, rendered only when
  `loginError` is set: `role="alert"`, using the same `text-sm font-medium text-destructive`
  treatment the field errors already use. Show the server's `detail` string when the response
  carries one, and a fixed fallback (`"Something went wrong. Please try again."`) otherwise —
  never render a raw Axios error, a status code, or a stack.
- Clear the form-level error when either input changes, so a stale "Incorrect email or
  password" does not sit under a corrected form.
- If `status === 'authenticated'` when the page renders, redirect immediately: `admin` →
  `/dashboard`, `tutor` → `/schedule`. Otherwise a logged-in user who navigates to `/login`
  sits on a login form they cannot escape.
- Never render, log, or place the password in a query string.

The API returns 401 `{"detail": "Incorrect email or password"}` for a wrong password, an
unknown email, and a deactivated account alike. **Render it as-is and add nothing.** Do not
help the user by distinguishing "no such account" — the backend deliberately does not, and
re-deriving the distinction in the UI would undo it.

## Verification

**Changed-risk surface.** The token lifecycle in the browser. The two failures that will not
show up in a build are (a) a refresh loop or an unhandled 401 that silently logs users out,
and (b) a rotation collision from a double-fired refresh, which looks exactly like a backend
bug and will be debugged in the wrong place.

**Static gate — runnable the moment the tasks land, no backend required:**

1. `docker compose run --rm dashboard npx tsc -b` — **not** `tsc --noEmit`, which checks
   nothing here. Treat a green `tsc --noEmit` as no evidence at all.
2. `docker compose run --rm dashboard npm run lint`
3. `docker compose run --rm dashboard npm run build`
4. `grep -rin "localstorage\|sessionstorage" dashboard/src` → empty
5. `grep -rn "from 'axios'" dashboard/src` → only `src/lib/api.ts`
6. `git diff --name-only dashboard/package.json dashboard/package-lock.json` → empty

**Live smoke — requires Plan 02-03 landed and a seeded admin.** Bring the stack up, run
`alembic upgrade head`, run the seed command from `02-03-PLAN.md`, then with `npm run dev`
serving on 5173:

- `http://localhost:5173/login`, correct credentials → lands on `/dashboard`. In devtools,
  `POST /auth/token` has request content-type `application/x-www-form-urlencoded` and a
  `Set-Cookie` for `refresh_token` marked HttpOnly.
- Wrong password → stays on `/login`, shows `Incorrect email or password` in the form-level
  alert, and the submit button re-enables.
- **Reload the page while logged in** → still on `/dashboard`, not bounced to `/login`. The
  network panel shows **exactly one** `POST /auth/refresh`. **Two refresh calls here is a
  FAIL** — it means the StrictMode guard is missing, and under rotation the second call burns
  the family.
- `Application → Cookies` shows `refresh_token` with `HttpOnly` ✓, `SameSite=Lax`,
  `Path=/auth`, and no `Secure` (local HTTP, `DEBUG=true`). `localStorage` and
  `sessionStorage` are both empty.
- Force an expired access token: in the console, `useAuthStore.setState({accessToken: '<a
  token minted with a past exp>'})`, or simply wait past 15 minutes, then trigger any `api`
  request. It must transparently refresh once and succeed. Phase 2 has no `/api/*` endpoint,
  so exercise this by calling `api.get('/api/anything')` from the console and confirming the
  401→refresh→retry sequence in the network panel; the final 404 from the retried request is
  the expected outcome and is fine.
- Log in, then log in again in a second browser profile as the same admin, then log out in
  the first. The second session must keep working — separate families (D-017).

**Browser tooling note.** REQ-010 remains unverified because no browser automation tool has
been available in any session (`STATE.md`). The static gate above is fully runnable without a
browser and should be treated as this plan's hard gate; the live smoke is the acceptance
evidence and needs either the Claude-in-Chrome extension connected or a human at a keyboard.
Do not substitute headless CDP — the user ruled it out.

**PASS requires:**

- **REQ-027** — access token in memory only (grep gate 4 is part of the proof); refresh token
  in an HttpOnly cookie the JavaScript never reads; silent refresh on 401; redirect to
  `/dashboard` for admin and `/schedule` for tutor.
- The single-refresh-on-reload check. Two refreshes is a defect, not a cosmetic issue.
