### What to build

**`docker/api.Dockerfile`** — base `python:3.12-slim`. Install `uv` (copy from
`ghcr.io/astral-sh/uv:latest` or the official installer). Set `WORKDIR /app`. Copy
`pyproject.toml` and `uv.lock` first and run `uv sync --frozen --no-install-project` so the
dependency layer caches independently of source changes. Then copy the rest of `api/`.
Default command: `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload`.
Build context is `./api`.

**`docker/dashboard.Dockerfile`** — base `node:22-alpine`, `WORKDIR /app`, copy
`package.json` + `package-lock.json`, `npm ci`, copy the rest. Default command:
`npm run dev -- --host 0.0.0.0 --port 5173`. Build context is `./dashboard`. Dev target
only — the production build image is Phase 8, REQ-080.

**`docker-compose.yml`** at the repository root. Exactly four services, named
`postgres`, `redis`, `api`, `dashboard`.

- `postgres`: `postgres:17-alpine`; env from `POSTGRES_USER`, `POSTGRES_PASSWORD`,
  `POSTGRES_DB`; named volume `pgdata:/var/lib/postgresql/data`; port `5432:5432`;
  healthcheck `pg_isready -U $POSTGRES_USER -d $POSTGRES_DB`, interval 5s, retries 10.
- `redis`: `redis:7-alpine`; port `6379:6379`; healthcheck `redis-cli ping`; no volume —
  conversation state is intentionally ephemeral per `docs/erd.md`.
- `api`: builds `docker/api.Dockerfile` with context `./api`; port `8000:8000`;
  `depends_on` both with `condition: service_healthy`; bind mount `./api:/app`; env
  `DATABASE_URL`, `REDIS_URL`, `SECRET_KEY`, `DEBUG`, and the three Twilio variables, all
  sourced from `.env` via `${VAR}` interpolation. The in-network `DATABASE_URL` host is
  `postgres` and the `REDIS_URL` host is `redis`.
- `dashboard`: builds `docker/dashboard.Dockerfile` with context `./dashboard`; port
  `5173:5173`; bind mount `./dashboard:/app` **plus an anonymous volume at
  `/app/node_modules`** so the host bind mount does not shadow the image's installed
  dependencies — this is the single most common failure mode of this setup; get it right.
  Env: `VITE_API_PROXY_TARGET=http://api:8000`.

Do not add a `version:` key (obsolete in Compose v2). Do not run migrations automatically
in any service command (D-009) — migrations are applied by
`docker compose run --rm api alembic upgrade head`, which you document in `.env.example`
comments only if it fits naturally; the authoritative place is `Readme.md`, owned by T3.2.

**`.env.example`** — every variable `Settings` requires plus the Compose and Vite ones,
using exactly the names frozen in `01-CONTEXT.md`. Safe placeholders only, and
`SECRET_KEY=change-me-generate-with-openssl-rand-hex-32`. No real credential may appear.
Keep it byte-for-byte consistent with the "Environment Variables" section T3.2 writes into
`Readme.md`; both derive from this list.

**`.gitignore`** (root) — `.env`, `.env.*` (but not `.env.example`), `__pycache__/`,
`*.pyc`, `.venv/`, `.pytest_cache/`, `.ruff_cache/`, `node_modules/`, `dist/`, `.DS_Store`.

**`.dockerignore` files** — root, `api/`, and `dashboard/`. Exclude `.git`, `.env`,
`node_modules`, `.venv`, `__pycache__`, `dist`, `.planning`, `docs`. Keeping build contexts
small matters here because both contexts are bind-mounted during development anyway.

### Acceptance criteria

- `docker compose config` parses with no warnings and resolves every `${VAR}` from a `.env`
  copied from `.env.example`.
- `docker compose up -d` reports `postgres` and `redis` healthy, and `api` starts only
  after both are.
- `docker compose exec dashboard ls node_modules | head` lists packages — proof the
  anonymous volume protected them from the bind mount.
- `docker compose down` then `up` preserves database contents; `docker compose down -v`
  destroys them.
- Editing `api/app/main.py` triggers uvicorn reload; editing a `dashboard/src` file
  triggers HMR.
- `git status` is clean after a full build. `git check-ignore -v .env` confirms the rule.
- `grep -rEi "(password|secret|token|sid)\s*=\s*[A-Za-z0-9]{12,}" .env.example` finds
  nothing that looks like a real credential.

### Out of scope

No production compose overlay, no multi-stage build for the dashboard, no nginx or Caddy —
all Phase 8. No CI configuration. No GitHub Actions. No `Makefile` or task runner. No
health check on the `api` or `dashboard` services themselves (their startup ordering does
not depend on it in dev, and a wrong one blocks the stack).

## Verification

**Changed-risk surface:** the developer's first-run experience and secret leakage. The
expensive failures are a stack that does not come up from a clean clone, and a credential
committed to `.env.example`.

**Commands, narrowest first:**

1. `docker compose config -q` — parses clean.
2. `git check-ignore -v .env` — the ignore rule exists.
3. `grep -c "" .env.example` and a manual diff against the Readme's variable block — same
   names, same order.
4. `docker compose build` — both images build.
5. `docker compose up -d` then `docker compose ps` — four services, `postgres` and `redis`
   healthy.
6. `docker compose exec dashboard ls node_modules | head -5` — non-empty.
7. `docker compose run --rm api alembic upgrade head` — succeeds (requires T1.2).
8. `git status --porcelain` — empty.

**Clean-clone smoke** (the real gate for this plan):

```
git clone <repo> /tmp/tutorlink-smoke && cd /tmp/tutorlink-smoke
cp .env.example .env
docker compose up -d
docker compose run --rm api alembic upgrade head
curl -s localhost:8000/health/ready
open http://localhost:5173/login
docker compose down -v
```

Follow `Readme.md` literally while doing this. If any step in the Readme is wrong or
missing, that is a T3.2 failure, not an operator error.

**PASS requires:** REQ-011 (all four services up, healthchecks honoured, `node_modules`
intact, volume persistence and destruction both correct, hot reload working), REQ-012
(`.env` ignored, no credentials in `.env.example`, clean `git status`), REQ-013 (the
clean-clone smoke completes using only the Readme, with no reference to `bot/` remaining).
